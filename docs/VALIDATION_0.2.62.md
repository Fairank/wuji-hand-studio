# 0.2.62 连续使用与异常恢复

在 0.2.61 后主动扩查不同操作顺序、跨服务回复和持久记录损坏，发现后先保留失败证据，再修复并独立复查。本轮不增加设备连接策略或新的功能页面，沿用官方 CLI、SDK 与既有控制链。

## 修复的实际问题

- CLI 更新已激活或回退已生效，但释放原占用文件失败时，旧实现没有可重试归属，后续操作可能永久等待。现在保留原完整占用及已提交结果，只有明确检查、重试或退出才能核对释放；后台任务、只读页面和其它工作区不能清理。回退后的释放重试不会再次交换版本。退出时先核对该占用，失败则不拆卸其它会话。
- 退出未完成时保留自动检查线程，但关闭状态期间不派发新的自动任务。明确检查恢复后，原更新偏好继续生效；确认退出成功才结束自动检查线程。
- 备份记录原来只核对少量字段，缺少人员、左右手或完整元数据时，可能出现未捕获错误，甚至进入原版导入后才发现记录损坏。现在严格校验本软件记录的结构、类型、重复字段与读取前后一致性，异常在导入启动前拒绝；原 ZIP 和损坏记录保持，不猜测或重建官方档案。
- 标定开始请求挂起后，页面断线再连接新服务，旧“取消开始”和旧回复可能继续使用新服务身份。现在每个异步操作和等待槽位绑定原服务与本次意图，旧成功、旧失败和旧收尾不能覆盖或阻塞新任务；合法的同服务任务归属重核仍可接收本次准确回执。
- 运行中的取消请求原来不携带准确标定编号，排队后可能取消后续新运行。当前页面分别使用准确开始请求或运行编号取消，后端在最终取消写入及资源清理前再次核对。取消先于开始到达时保留有界的本次取消记录，迟到开始不能再启动；近期重复的同一次开始也不会再次执行。内部明确全局停止保持原含义。
- 备份恢复按钮原来的局部等待不随服务或备份更换而退休，旧请求可能让新任务等待至超时。按钮现按原服务、运行和备份摘要管理等待；旧回调不能清理新恢复请求的状态。

## 新顺序与验证边界

实际 Controller、Handler、文件协调、标定服务及原生工作线程在隔离 SDK、文件、进程和网络替身下执行，覆盖更新激活、回退、释放失败、明确重试、错归属、损坏记录、旧取消晚到及最终资源边界。页面使用完整源 HTML、JS、CSS 和真实回环 HTTP；原版确认与终端输出由替身提供，未对真实档案或设备操作。

另执行 8 轮明确手套连接，每轮两次配对、跟随、停止和解除配对：合计 16 次模拟灵巧手会话，模型只导入一次，未自动重连，最终所属工作线程均退出。模拟 SDK 端点使用有界接收队列和合成反馈；这验证软件生命周期，不是实际网络、长期稳定性或真实动作质量的证明。

连续页面检查覆盖简单/完整模式、中英、窄宽、设备选择、人员新增/覆盖、同页虚拟与实机、菜单关闭、任务列表及视图关闭重开。没有触发浏览器原生下载或 IDM，文件导出分别用代码保存、摘要和 ZIP CRC 检查。

原始失败、测试夹具的无效入口或时序假设、修复后记录及非作者复查分别保留。实际 SDK/CLI、硬件连接、固件刷写、真实标定采集与实机动作本轮未执行。软件构建、安装后的版本与载荷、配置和标定资料保留、源码同步另由外部交付记录确认，源码版本不表示已公开发布安装包。

最终 Python 回归执行 2581 项，失败和错误为零，运行期间源码未变化。3 项环境跳过仍分别是未部署的原实物记录、Linux 专属文件锁条件、当前系统不允许创建测试符号链接；不能将这些条件计为已验收。总数与实际流程、界面和非作者记录分别保留，不作“永远没有缺陷”的承诺。
